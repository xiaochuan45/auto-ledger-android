# 产品需求与验收约束

需求基线：2026-10-16。本文记录用户已提出的目标与边界，属于计划及验收依据，不表示功能已经实现。

## 1. 产品定位与设备

开发一个简洁、实用、易用的 Android 手机本地自动记账工具，参考一木记账的使用体验。安装后在手机本地独立运行，不需要后端服务器。

- 主要使用设备：一加 Ace 5，Android 和系统具体版本后续按实机确认。
- 用户主要通过手机上的 Codex Cloud 发起任务。开发、自动化测试、编译及 APK 打包在云端完成，不依赖用户个人电脑开机。
- 交付可在手机上下载并安装的 APK，先验证实际可行的交付链路。
- 仓库：[xiaochuan45/auto-ledger-android](https://github.com/xiaochuan45/auto-ledger-android)。权限、环境和编译能力必须实际检查，不能沿用未经验证的结论。
- 缺少授权、签名配置或必需真机信息时，明确具体操作步骤；其余常规工作按已授权范围推进。

## 2. 自动识别范围

支付渠道包括微信、支付宝。常用消费平台包括淘宝、京东、拼多多、美团、抖音。

目标场景包括：

1. 用户扫商家收款码付款。
2. 商家扫用户付款码扣款。
3. 网上购物付款。
4. 平台内免密支付。
5. 会员续费等后台自动扣费。

优先评估 Android 无障碍服务、交易通知等系统允许的信息来源，具体采用和适配方式根据实测选择。后台扣费不能只依赖付款成功页面；应评估通知、账单导入等覆盖方式。部分应用、系统版本或交易可能不暴露可读信息，必须逐项说明已支持、待验证和无法自动捕获的范围，并提供导入或手动补记办法，不承诺所有场景实时捕获。

无障碍和通知服务只处理自动记账必要的应用、页面、事件及通知。权限需由用户在手机系统设置中手动开启，并提供清晰的入口、用途说明和恢复步骤。

## 3. 账单字段与时间来源

每笔账单至少能表达以下信息：

| 字段 | 要求 |
|---|---|
| 日期和时间 | 优先使用实际付款时间；只有识别时间时明确标注时间来源，允许修改 |
| 实际支付金额 | 使用优惠后的实付金额，精确到最小货币单位 |
| 商户或交易对象 | 记录可靠读取的信息，无法读取时留空或标为未知 |
| 消费平台 | 例如美团、淘宝，与支付渠道和分类分别保存 |
| 支付渠道 | 例如微信、支付宝，与平台和分类分别保存 |
| 消费分类 | 自动规则、手动选择或未分类 |
| 备注 | 支持用户编辑 |

展示示例：

> 2026-10-16 12:30｜美团外卖 23.50 元｜平台：美团｜支付：微信｜分类：餐饮

读不到的信息不编造。交易标识、来源类型、时间来源、资金类型和退款关联等必要结构化元数据可用于准确性与审计，但不长期保存原始页面或通知全文。

## 4. 分类

- 默认分类：餐饮、交通、购物、娱乐、生活缴费、学习、医疗、其他、未分类。
- 支持自定义分类。
- 优先使用本地商户规则、关键词等方式分类，不调用云端大模型。
- 修改分类时，用户可以选择是否记住该商户的分类规则；不应默认把一次修改推广为所有交易的规则。
- 不能仅凭「淘宝」「美团」等平台名称判断具体消费用途。
- 金额和交易状态明确、仅分类未知时，直接记为未分类，无需每笔确认。

## 5. 记账准确性

### 成功、金额与待核对

- 明确付款成功后自动入账，无需每笔确认。
- 失败、取消、待支付订单不计消费。
- 按优惠后的实际支付金额记账，不把原价、订单总价或优惠金额误当实付金额。
- 金额或交易状态不明确时进入待核对，不猜测入账。待核对项不计入已确认的消费统计。
- 一条信息同时含有多种金额、交易状态或不明确对象时，按明确证据判断，无法确认则待核对。

### 去重与交易独立性

- 同一交易被页面、通知、账单导入等来源重复识别时，只记一笔。
- 重复通知、重复事件、重新打开历史账单及再次导入同一账单文件不能重复记账。
- 连续两笔同金额的真实付款必须保留为两笔，不能按金额和短时间窗口直接合并。
- 优先使用可靠交易标识。没有稳定标识时需设计保守的来源关联与历史页面处理规则，并通过真机验证其边界。
- 用户删除的记录不能因历史页面重开而静默重新出现；保留必要的最小去重或撤销信息，并说明删除、撤销和重新导入的行为。

### 退款

- 支持全额退款、部分退款及同一消费的多次部分退款。
- 退款到账与退款申请分开；申请、处理中或失败不能直接记为到账退款。
- 退款按实际退款日期抵减当期支出，保留与原消费的关联。原消费发生在前一月或前一年时，也不得把退款归回原消费日期。
- 无法可靠匹配原消费时保留待关联信息，允许用户修正，不强行关联相似金额交易。
- 原消费、退款或导入记录被多个来源识别时，同样执行去重。

### 资金类型

- 充值、提现、本人账户之间转账与消费分开处理，避免重复计算。
- 给他人转账的实际用途允许手动指定。
- 当前不做花呗或信用卡管理。

## 6. 统计

- 提供每日、每周、每月、每年的支出、退款和净支出。
- 周按周一至周日；月和年按自然月、自然年。
- 退款按实际到账日期进入对应期间；净支出为该期间已确认支出减去该期间已确认退款，可以出现负值。
- 提供各分类的金额、占比与明细。占比分母及退款处理方式需要在界面明确，避免净支出为零或负数时产生误导；具体口径在实现时保持一致并记录。
- 充值、提现、本人账户间转账不作为普通消费累计；待核对项不进入确认统计。
- 统计与筛选使用明确的本地时间边界。支付时间和识别时间的来源保持可见，用户修正后相应更新统计。

## 7. 基础界面与操作

日常主要使用「账单」和「统计」两个页面，分类、权限、备份等放入设置。

- 查看、筛选账单和打开明细。
- 手动补记，修改金额、时间、分类和备注。
- 删除与撤销；删除、编辑和恢复应同步影响明细、统计和必要的去重状态。
- 默认付款成功后直接记录。记录完成提醒可以关闭。
- 显示自动记账权限、服务状态及可确认的异常；提供清晰的系统检查和恢复入口，不把状态指示灯作为后台始终可用的保证。
- 权限关闭、系统限制、服务中断或无可靠来源时说明影响和补记方式。

## 8. 存储、隐私与数据管理

- 识别、分类和存储全部在手机本地完成。
- 不调用云端大模型，不需要后端，不申请 `android.permission.INTERNET`。
- 不接广告、统计或云端日志服务；检查依赖合并后的 Manifest 和最终 APK，防止依赖意外带入联网权限。
- 只处理记账所需的应用、页面和通知，及时丢弃无关信息。
- 只保存必要账单字段和准确性所需的最小元数据；不长期保存整屏文字、截图、聊天内容、密码、验证码或原始通知全文。
- 支持微信、支付宝账单文件导入，并处理与已有记录及其他来源的重复。具体文件格式、编码和字段按脱敏样本确认，不能声称支持未验证的导出格式。
- 支持账单导出、本地加密备份及恢复。备份格式、密钥派生、口令和异常文件处理需经过验证，不使用自创加密算法。
- 禁用账目自动云备份；配置适用 Android 版本的备份与迁移规则，防止账目被系统自动上传。
- 后续版本更新尽量保留已有数据，并验证数据库迁移、签名和覆盖安装。
- 开发、CI、自动化测试只使用虚构、脱敏数据。真实账单保留在用户手机，不提交到 GitHub 或构建日志。

## 9. 开发顺序与交付验收

1. 先检查仓库访问权限、云端工具链、APK 编译、签名、上传及下载条件；交付最小可运行 APK，走通手机下载、安装和启动。
2. 再交付自动识别小样：识别付款信息、去重、本地保存和查看记录，提供手机权限设置、权限恢复及真机测试步骤。
3. 依据实际识别效果继续适配；逐步完善分类、统计、退款、导入导出和备份。
4. 测试覆盖扫码、被扫码、网购、免密、后台自动扣费、失败付款、重复识别、连续同金额付款及后台放置后的运行情况，详见 [测试矩阵](TEST_MATRIX.md)。

每轮交付必须说明：本轮完成内容、APK 下载方式、版本及签名用途、验证结果、已知限制和下一步，并明确区分三层证据：

| 证据层 | 能证明什么 | 不能替代什么 |
|---|---|---|
| 代码已实现 | 源码包含相应逻辑，能定位到实现 | 不能证明构建成功或真实场景可用 |
| 模拟或自动化测试通过 | 指定环境与虚构、脱敏样本下符合断言 | 不能证明微信、支付宝或用户手机实测通过 |
| 用户手机真机实测通过 | 指定手机、系统、应用版本和场景实际验证 | 不能泛化为所有版本、平台或后台场景可用 |

没有在用户手机验证过的支付场景，统一标为「真机待验证」。目前产品需求已记录，功能完成度与实际交付结果另行更新。
