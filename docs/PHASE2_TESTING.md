# 自动识别小样：手机设置与验证

已发布版本：`0.2.0-prototype`。通知恢复修复候选：`0.2.1-prototype` / versionCode `3`，开发与验证中，尚未交付。应用 ID：`io.github.xiaochuan45.autoledger`。最低安装要求 Android 8.0 / API 26。目标是支持不同品牌的 Android 手机；一加 Ace 5 是当前用户设备，不是功能前置条件。厂商系统设置名称、后台限制和付款应用版本会影响识别，需要分别记录。

用户已安装 `0.2.0` 小样并进入设置，开启总开关和两个渠道，通知与无障碍都曾显示已授权、已连接。清理后台后，一次拼多多微信付款跳转微信付款页但未记录；返回账本时通知已授权未连接、无障碍仍已授权已连接。该次漏记已记为失败，原因尚未唯一确定。其他支付场景不据此推断通过或失败。第一阶段 `.preview` 是另一个无账单的安装预览。

## 本次漏记先这样处理

本次付款手动补记即可，**无需重新消费**。重连服务不会回扫旧通知或找回这次已丢失的记录。

1. `0.2.0` 中确认自动记账总开关和所需渠道仍开启。若通知已授权但未连接，在系统通知使用权列表关闭再开启本应用，返回账本点“刷新权限状态”，查看实际连接状态。
2. 可按手机实际设置检查允许后台活动；部分品牌可在最近任务中锁定应用。这些是可选排查方式，菜单和效果因品牌而异，不保证服务不被中断。
3. `0.2.1` 发布后，使用同签名 versionCode `3` 直接覆盖 `0.2.0`，不要卸载或清除数据。在通知权限已开启但服务未连接时，使用新版本独立的“尝试恢复”操作；等待真实连接回调后才算已连接，请勿把按钮点击成功当作已恢复。当前候选尚未完成代码与 CI 验证，新版具体按钮以交付界面为准。

离开账本界面、按 Home 或切换应用不等于清理后台。划掉最近任务、系统一键清理及设置中的“强行停止”也可能有不同效果；强行停止或厂商限制不能靠重连请求绕过。无需让账本界面一直开着，但系统需要允许相关服务后台运行。

## 第一轮只做三项检查

1. 安装本版“本地账本·小样”，手动补记一笔测试账单，关闭重开后确认仍在，再删除这笔测试记录。
2. 按下文开启总开关、渠道、通知使用权和无障碍，返回设置刷新，检查两项服务的授权与连接状态。
3. 等下一次日常微信或支付宝付款，查看是否记录、金额是否正确、有没有重复或待核对。无需专门消费；没有识别时手动补记即可。

已有安装与授权结果无需重复验证；先完成尚未确认的项目即可，恢复后等下一次正常日常使用，不为本次漏记重新消费。具体系统和支付应用版本可在后续兼容排查时补充，不作为开始恢复的前置条件；不要发送验证码、聊天内容或完整真实账单，用户已提供的设置截图不提交仓库。后面的详细矩阵可随日常使用逐项验证。

## 安装与更新

1. 从本轮 [GitHub Releases](https://github.com/xiaochuan45/auto-ledger-android/releases) 下载已公开版本的 `auto-ledger-prototype.apk`，核对版本；`0.2.1` 当前尚未交付，不将草稿链接当作已可下载。不要安装 CI 调试包或 `verification-*` 自动化测试附件。
2. 系统询问时，仅为当前用于安装 APK 的浏览器或文件管理器开启“允许安装未知应用”。安装完成后可关闭该安装来源的权限。
3. 本版与旧“本地账本·预览”并列安装。旧预览没有真实账单，不能把它当作本版的覆盖升级验证。
4. 后续相同包名、相同签名且版本号更高的 APK 应直接覆盖安装。不要先卸载，也不要清除数据；这些操作会丢失本地账单。本阶段尚无导出或加密备份，不宜作为唯一账目来源。
   `0.2.1` 需要与已安装 `0.2.0` 同签名，从 versionCode `2` 覆盖到 `3`；本轮真实覆盖更新验证待交付时记录，不能用旧的升级 fixture 结果代替。
5. 初次启动确认账单列表为空，打开统计、设置后返回，再关闭重开。应用不会预置模拟消费或在授权时导入旧通知。

## 开启自动记账

自动记账默认关闭。仅在希望试用时执行：

1. 进入应用“设置”，阅读本地处理说明，开启“自动记账总开关”，选择微信、支付宝渠道。关闭总开关或某渠道会停止相应后续采集，手动补记仍可用。
2. `0.2.0` 点击“检查 / 恢复通知使用权”，在系统列表选择“本地账本”并允许通知读取；该旧按钮只打开权限设置，不能主动请求重连。`0.2.1` 正在把打开权限设置和尝试恢复连接拆为独立操作。Android 提供的是系统级通知使用权；代码先按包名与交易通知标题筛选，只处理微信、支付宝的必要付款信息，不读取聊天消息附件或历史通知列表。
3. 点击“检查 / 恢复无障碍服务”，在系统无障碍页面找到“本地账本”并开启。代码和 APK 配置限定微信、支付宝，以及白名单付款页面和必要事件；不获取截图、不执行手势、不读取输入框、密码框或聊天页面。
4. `0.2.0` 返回应用点“刷新权限状态”。分别查看“已授权”和“服务已连接”；授权成功并不保证服务正在连接，也不保证所有付款场景可读。`0.2.1` 正在改为根据真实回调自动更新状态，恢复请求与实际连接分开显示，效果待验证。
5. 按需要打开“检查电池与后台限制”。在手机系统里检查该应用的后台活动、电池使用及自启动选项，菜单名称依品牌和系统版本变化。应用不会为此申请新权限，也不能代替系统设置。

某些 Android 13 及以上系统对浏览器下载的 APK 限制无障碍或通知读取。若明确出现“受限制的设置”，可在系统“应用信息 → 本地账本 → 右上角菜单”查找“允许受限制的设置”，确认安装来源后再授权。部分系统可能没有相同入口，按系统实际提示操作；不要据此关闭系统整体安全防护。

通知识别依赖支付应用实际发出、系统允许暴露的交易通知。是否隐藏通知内容、关闭支付通知、应用版本变化等均可能导致不可读。无障碍识别还依赖页面类名与可访问文字；不支持的页面直接忽略，不为提高覆盖率而扩大到聊天或普通网页。

`0.2.1` 的通知重连使用 Android 官方 `requestRebind`，受总开关、渠道和系统授权约束，30 秒节流，每个断开周期自动尝试一次；它不申请新权限、不扩大白名单、不读取旧通知，也不能绕过强行停止或系统后台限制。这是当前修复方案，代码与验证尚未完成，不作为真机恢复成功的结论。

## 账单检查和纠正

- 已确认消费：状态与实付金额明确时自动保存，分类初始为“未分类”。平台、支付渠道和分类分别显示；没有可靠商户或平台时显示“未知”。
- 待核对：金额、状态、历史页面或重复关联存在歧义时，不计入已确认支出。打开明细后核对真实付款，可改金额、时间、商户、平台、分类和备注，再确认。
- 同一交易号、同一来源事件重复时复用已有记录。缺少共同交易号的跨来源相似记录不会凭金额和时间自动合并，可能进入待核对；确认为同笔可“合并到原账单”，确认为另一笔可“保留为独立交易并核对”。
- 时间标注为付款时间、识别时间或用户修改时间；只有识别时间时不要将其当作支付平台的准确付款时间。
- 可从账单页右下角手动补记。删除后可在底部提示中撤销；去重所需的最小结构化标识仍用于阻止已删交易被相同来源重新导入。
- 退款、转账、充值和提现本阶段保留待核对，不自动作为消费；退款到账关联和抵减统计尚未实现，不要为了清除待核对而把退款改成支出。

## 没有自动记录时

先确认总开关和渠道开关，再检查两项授权与连接、付款应用的交易通知和系统后台限制。`0.2.0` 可在系统中关闭再开启通知使用权，回应用手动刷新；`0.2.1` 交付后，通知仍授权但未连接时可点独立恢复按钮，观察真实连接回调。恢复请求可能被节流，系统也可能未重新连接，不能只凭点击动作判为成功。恢复不会回扫历史通知或补抓已漏掉的交易。

若仍未记录，使用手动补记，反馈场景、渠道、状态和必要版本。没有可读信息时本版不能捕获；账单文件导入将于后续实现。请勿反复重付或授权无关应用来“修复”识别。

## 自动化及签名验证方法

普通 CI 分别在 API 26 与 API 35 模拟器运行 Room、界面和隐私范围测试，并运行 JVM 解析测试、Lint、debug 与 unsigned release 的最终包审计。矩阵代表这些模拟 Android 环境，不覆盖各品牌系统和真实支付页面。是否通过以具体 Actions 结果为准，本文不提前宣称通过。

```bash
./gradlew testDebugUnitTest assembleDebug lintDebug assembleRelease
./gradlew connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.notClass=io.github.xiaochuan45.autoledger.data.UpgradePersistenceTest
python3 scripts/verify_apk.py --apk app/build/outputs/apk/debug/app-debug.apk --output-dir evidence/debug
python3 scripts/verify_apk.py --apk app/build/outputs/apk/release/app-release-unsigned.apk --output-dir evidence/release --build-type release --unsigned
```

正式交付签名 APK 在云端私有签名后上传 Draft Release；带 `release_tag` 与公开 `certificate_sha256` 输入的工作流只下载该草稿的 APK，不重新编译，先复核权限、备份与证书，再在 API 35 模拟器安装它执行 release instrumentation。公开指纹参数还必须匹配主源码 checkout 中的 `config/signing-certificate.sha256`。测试与升级 fixture 也必须用同一证书签名。

若开发环境无法直接上传 Release 附件，可把已经签名的三份 APK 与正式包校验文件放到本仓库临时 orphan 分支，提供其精确 40 位 commit SHA 作为可选 `delivery_ref`。工作流把它单独 checkout 到 `staging/`，只复制固定四个文件：`auto-ledger-prototype.apk`、`auto-ledger-prototype.apk.sha256`、`verification-instrumentation.apk`、`verification-upgrade.apk`。验证脚本始终来自主源码 checkout，不执行或恢复 staging 中的脚本、工作流或配置。

此替代路线先校验文件类型、严格格式的正式包校验文件、主源码中的公开证书 pin、三包身份及正式 / 升级包的权限和备份资源，再由 GitHub runner 上传到已经存在的草稿。随后仍重新下载附件，逐字节比较四个文件，再执行原来的签名包和覆盖升级测试。`delivery_ref` 为空时直接沿用草稿下载路线。临时分支只能放可公开的已签名 APK 和校验文件，禁止存放私钥、口令、令牌或真实账目；验证后清理该分支。

`0.2.0` 的脚本先运行普通测试（排除顺序敏感的 `UpgradePersistenceTest`），再单独执行 `seedBeforeUpgrade`，真实 `adb install -r` 安装 versionCode 3 fixture，最后执行 `dataSurvivesUpgrade`，核对虚构账单、编辑字段、待核对、删除与去重信息保留。该历史 fixture 不是本轮 `0.2.1`，本轮从已发布 code 2 到修复版 code 3 的同签名覆盖结果需另行记录。该过程只验证相应数据库格式下的数据保留，不是未来 schema 迁移测试。

```bash
python3 scripts/verify_delivery_signatures.py --directory delivery --expected-cert-sha256 PUBLIC_CERTIFICATE_SHA256
bash scripts/verify_delivery.sh delivery
```

CI 仅上传审计及测试证据，不自动发布调试包。正式发布前移除草稿中的 `verification-instrumentation.apk`、`verification-upgrade.apk`；普通用户只安装交付 APK。
