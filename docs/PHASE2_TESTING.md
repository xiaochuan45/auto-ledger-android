# 自动识别小样：手机设置与验证

最新版本 `0.2.2-prototype` / versionCode `4`，包名 `io.github.xiaochuan45.autoledger`，最低 Android 8.0 / API 26。不绑定手机品牌；不同系统和支付应用版本仍需分别验证。

`0.2.1` 已在用户手机安装，两项服务显示已授权、已连接，但再次拼多多 → 微信付款仍未记录。旧计数均为 0 发生在筛选之后，不能据此确定系统未发事件。本版增加分阶段计数和只读兼容性检查，**不是已经修复该支付路径的声明**。代码、自动化和真机状态见 [本轮说明](RELEASE_0.2.2.md)。

## 本次只做已有付款的只读检查

1. 从 [本版 APK](https://github.com/xiaochuan45/auto-ledger-android/releases/download/prototype-v0.2.2/auto-ledger-prototype.apk) 下载并直接覆盖旧版，不要卸载或清除数据。
2. 设置中确认自动记账总开关、微信渠道开启；通知与无障碍均已授权、已连接。
3. 点「开始只读检查（5 分钟）」，确认显示「检查中 · 暂停自动记录」。
4. 切到微信：我 → 服务（旧版可能叫支付）→ 钱包 → 账单，打开这次已有付款的详情，然后回到账本。无需再次消费；期间不要清后台。
5. 点「刷新检查结果」，结束检查，再点「复制无账单原文的诊断摘要」，将摘要发回开发对话。程序类型为空也保留原样，不发送付款截图或完整真实账单。

只读检查暂停自动记录，不读取付款正文或截图，也不新增检查账单；手动补记仍可用。最多 5 分钟，结束、超时或进程重启后按原开关恢复工作。结果仅在当前进程内，最多 6 个程序类型名；可主动清除。摘要只含版本、Android API、事件计数、固定跳过原因和规范程序类型名。

这一步只帮助定位输入和筛选阶段，不能验证未来所有付款可记录，也不会补抓之前漏记的交易；已漏记的付款请手动补记。

## 安装与更新

只安装公开 Release 的 `auto-ledger-prototype.apk`；不要安装普通 CI 的调试包或 `verification-*` 测试附件。系统询问时，为当前浏览器或文件管理器允许安装未知应用，完成后可关闭该来源的安装权限。

同包名、同签名且版本号更高时直接覆盖安装，保留本地数据。准确公开旧 0.2.1 / code 3 → 本版 code 4 已通过模拟器真实覆盖更新检查，保留虚构账单、去重标识及总/渠道开关；这不等于用户手机升级已实测。第一阶段 `.preview` 是并列应用，没有自动记账。

本阶段尚无导出或加密备份，请保留其他账目来源，不把小样作为唯一账本。

## 开启与恢复自动记账

采集默认关闭。首次使用时，进入设置，开启自动记账总开关及需要的微信、支付宝渠道，再授予系统通知使用权并启用无障碍服务。后续由系统通知或受支持付款窗口事件触发，不要求账本界面一直打开，也不循环读屏。

通知项分开提供「打开通知权限设置」与「尝试恢复通知监听」。已授权但未连接时才尝试恢复，以真实连接回调为准；点击成功不代表服务已经连接。恢复请求受总开关、渠道和授权约束，30 秒节流，每个断开周期自动尝试一次；不读取旧通知，不补记旧交易。权限状态可手动刷新。

某些 Android 13 及以上系统若明确提示「受限制的设置」，可在系统应用信息右上角菜单查找「允许受限制的设置」，确认安装来源后再授权；入口以系统实际提示为准。

离开界面或切换应用与清理后台、系统强行停止不同。可按手机实际设置允许后台活动；部分系统可在最近任务锁定应用，但不保证绕过厂商限制。通知恢复不能绕过强行停止或省电限制。无可读交易通知或受支持页面时无法捕获，服务已连接也不保证所有场景可识别。

## 账单检查和纠正

- 已确认消费：状态与实付金额明确时自动保存，分类初始为“未分类”。平台、支付渠道和分类分别显示；没有可靠商户或平台时显示“未知”。
- 待核对：金额、状态、历史页面或重复关联存在歧义时，不计入已确认支出。打开明细后核对真实付款，可改金额、时间、商户、平台、分类和备注，再确认。
- 同一交易号、同一来源事件重复时复用已有记录。缺少共同交易号的跨来源相似记录不会凭金额和时间自动合并，可能进入待核对；确认为同笔可“合并到原账单”，确认为另一笔可“保留为独立交易并核对”。
- 时间标注为付款时间、识别时间或用户修改时间；只有识别时间时不要将其当作支付平台的准确付款时间。
- 可从账单页右下角手动补记。删除后可在底部提示中撤销；去重所需的最小结构化标识仍用于阻止已删交易被相同来源重新导入。
- 退款、转账、充值和提现本阶段保留待核对，不自动作为消费；退款到账关联和抵减统计尚未实现，不要为了清除待核对而把退款改成支出。

## 真机测试顺序与当前事实

先完成上面的只读检查。后续测试结合正常日常付款逐项验证，无需专门消费；不上传真实金额、交易号、完整账单、原始通知、聊天或验证码。

| 场景 | 当前真机事实 / 待验证内容 |
|---|---|
| 安装、授权、连接 | 0.2.0、0.2.1 已安装并有两项服务连接截图；0.2.2 待验证 |
| 拼多多 → 微信付款 | 0.2.0 清后台后漏记；0.2.1 连接显示正常后再次漏记；0.2.2 尚未验证，未宣称修复 |
| 本版只读检查 | 待用户按上述步骤执行，以摘要区分原始事件、支持页面和筛选原因 |
| 手动补记、编辑、删除撤销 | 用户手机细项待验证 |
| 扫码、被扫码 | 微信、支付宝分别待验证 |
| 淘宝、京东、美团、抖音购物 | 平台与支付渠道分别核对；全部待验证 |
| 免密、会员续费、后台扣费 | 需要可读来源；全部待验证 |
| 失败、取消、待支付 | 不应新增已确认支出；待验证 |
| 优惠、实付并存 | 应用实付；歧义留待核对，待验证 |
| 重开历史、同笔跨来源、连续同额 | 不重复入账、不误合并真实两笔；待验证 |
| 后台、锁屏、清理、跨夜及重启 | 操作和时长分别记录；0.2.0 曾通知断连，其余待验证 |

完整验收要求见 [测试矩阵](TEST_MATRIX.md)。必要反馈模板：

APK 版本：

## 没有自动记录时

检查总开关、渠道、授权和实际连接；不要反复付款或授权无关应用。恢复不会补抓旧交易。仍漏记时手动补记，使用本版只读诊断反馈固定摘要；没有可读信息的场景无法自动捕获。账单导入、退款关联、完整分类统计及加密备份尚属后续工作。
