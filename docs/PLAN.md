# 实施规划

规划基线：2026-10-16。用户已授权将规划补充到仓库，并准备第一阶段工作。本文中的任务和时间是实施计划，实际完成状态须由代码、构建产物和测试记录证明。

完整需求见 [REQUIREMENTS.md](REQUIREMENTS.md)，测试与证据要求见 [TEST_MATRIX.md](TEST_MATRIX.md)。

## 技术方向

- 原生 Android：Kotlin、Jetpack Compose、Room 本地数据库。
- 采用通知监听和无障碍服务读取必要付款信息；具体优先级、来源组合和可覆盖范围由真机实测决定。
- 本地规则负责金额、状态、商户等字段识别及分类。不使用后端或云端大模型，不申请联网权限。
- 分开组织信息采集、交易识别、去重、账务存储和统计，便于给不同来源使用相同的账务规则。
- 金额精确存储；平台、渠道、分类、资金类型和时间来源分别表达。保留必要的结构化交易标识，避免持久保存原始页面或通知。
- 优先云端构建并通过 GitHub Releases 附件交付 APK；第一阶段实际验证权限、上传和手机下载可达性。若必须使用临时交付方式，说明有效期及限制。
- 尽早确定稳定包名和持续使用的安装签名，保障覆盖更新；私钥和口令通过安全的凭证存储管理，不提交到仓库。

## 第一阶段：走通 APK 交付

目标：用户不需要个人电脑，即可在手机上下载、安装并启动最小应用。

工作范围：

1. 检查仓库读取、写入、工作流和发布附件权限，记录真实结果；缺少必需授权时说明具体步骤。
2. 检查云端 JDK、Android SDK、Gradle 和网络可用性，选择可复现的编译方式；必要时配置 GitHub Actions。
3. 创建最小 Android 工程与清晰的应用身份，展示「账单」「统计」入口及设置入口。未实现能力须明确标注，不用示例数据冒充真实账目。
4. 确定首版 Android 兼容范围，待用户确认实机系统后校验兼容性。
5. 禁用账目自动云备份；检查源码、合并 Manifest 和最终 APK 的权限，确认没有 `INTERNET`。
6. 构建并签名 APK，记录应用包名、版本号、最低系统要求、签名用途、文件校验值和源码提交。
7. 上传真实可下载的 APK，提供手机下载、安装与启动步骤及可预期的系统提示。
8. 保留用户确认的安装和启动结果；未收到真机反馈前，仅标记为「云端构建通过，真机安装启动待验证」。

验收：

- 云端构建成功，产物可定位且可下载。
- 最终 APK 权限检查通过，签名用途和后续更新方式有明确记录。
- 手机下载安装及启动步骤可执行。
- 用户在一加 Ace 5 上确认成功安装启动后，才关闭第一阶段真机验收项。

第一阶段不把自动支付识别、分类或完整统计写为已完成。仓库、环境、构建及交付的实时结果记录在对应交付文档中。

## 第二阶段：自动识别小样

目标：以可验证的小范围场景走通「来源事件 → 成功判断 → 金额提取 → 去重 → 本地保存 → 查看记录」。

工作范围：

- 接入通知监听、无障碍服务，按支持应用及必要事件限制读取范围。
- 优先适配微信、支付宝中具有明确成功状态、实付金额和必要标识的来源，支持关闭与恢复权限。
- 保存金额、时间及来源、商户、平台、渠道、分类等最小字段，缺失信息留空或标为未知。
- 明确成功且金额清楚时自动入账；金额或状态不明进入待核对；分类不明记为未分类。
- 设计稳定交易标识去重，以及没有交易号时的保守来源关联；验证历史页面重开与连续同金额付款。
- 提供账单列表、详情、必要的手动更正和权限状态入口，默认无需逐笔确认。
- 提供以虚构、脱敏文本为输入的自动化测试和适用于用户手机的步骤。

验收：

- 自动化测试验证成功、失败、待支付、实付金额、重复事件和同金额独立交易。
- 无原始页面、通知全文或敏感数据被长期保存和写入日志。
- 可下载安装测试 APK，并在场景清单中逐项标出支持、待验证或已知不可读的来源。
- 至少一个明确范围的真实支付场景，经用户手机验证后才标为「真机通过」。尚未真机验证不阻止交付测试版，但必须明确状态。

## 第三阶段：真机适配与后台验证

目标：根据一加 Ace 5 的 Android、系统版本及应用实际表现修正识别规则，建立可信的覆盖边界。

- 覆盖微信、支付宝的扫码、被扫码、网上购物、免密、会员续费和其他后台扣费目标。
- 对淘宝、京东、拼多多、美团、抖音分别记录消费平台与实际支付渠道，避免平台名误分类。
- 测试跨页面、通知和导入的重复；测试历史页面、连续同金额付款和识别中断后的恢复。
- 检查通知权限、无障碍状态、系统电池限制及后台放置后的运行情况，提供清楚的恢复入口。
- 不能自动读取的场景，明确无信息来源、状态不清或系统限制等原因，并提供导入、待核对或手动补记路径。
- 用户只需反馈必要的结构化信息；不要求上传真实完整账单、整屏文字、聊天或验证码。

验收：测试矩阵包含手机与应用版本、具体场景、结果、重复或漏记情况及限制；不将单个版本的成功推广为所有场景可用。

## 第四阶段：完善日常使用

目标：形成可持续试用的首版。

- 分类：默认和自定义分类，本地商户规则，修改分类时可选择记住商户。
- 操作：账单筛选、手动补记、金额和时间修改、备注、删除撤销、可关闭的入账提醒。
- 统计：日、周、月、年；支出、退款、净支出；分类金额、占比和明细；自然周期和周一至周日。
- 退款：全额、部分和多次部分退款到账，原消费关联，跨期统计与重复退款识别。
- 资金类型：充值、提现、本人账户间转账分离，给他人转账支持指定用途。
- 数据管理：微信、支付宝账单文件导入、跨来源去重、导出、本地加密备份和恢复。
- 升级：数据库迁移、稳定包名与签名、覆盖安装保留数据。

验收：关键账务规则通过自动化测试，核心界面和升级恢复通过设备验证；导入格式及支付场景的支持程度逐项记录。

## 第五阶段：回归与稳定性

- 回归高风险边界：优惠实付、退款申请、跨期退款、相同金额、时间不明、重复导入、删除后重识别、权限撤销与恢复。
- 观察后台放置、锁屏、跨夜、重启后服务状态及恢复，不用短时前台测试替代长期验证。
- 验证加密备份的正确口令、错误口令、损坏文件、中断恢复及版本兼容；确保失败不破坏现有数据。
- 检查最终 APK 权限、敏感日志、自动云备份规则、签名和覆盖升级。
- 发布版本说明、测试证据、支持范围、已知限制、下载方式和下一步。

验收：关键风险有实际检查结果，用户能识别当前服务状态并完成常见恢复；未知项明确保留，不承诺绝不漏记或覆盖全部交易。

## 初步时间估算

以下是在尚未完整验证 Android 工具链、下载链路及真机来源之前的工作量估算，不是完成承诺。一个开发日表示大致工作量，不表示后台有会话持续计时运行。

| 里程碑 | 初步估算 | 依赖 |
|---|---|---|
| 首个可下载、安装和启动的 APK | 开始执行后约 1–3 小时 | 仓库、编译、签名及下载链路可用；手机启动仍需用户确认 |
| 首个自动识别小样 | 累计约 1–2 个开发日 | 初始信息来源可读，完成必要规则测试 |
| 一轮主要支付场景适配 | 小样后另约 2–4 个开发日 | 用户真机测试反馈、系统及应用行为 |
| 含统计、退款、导入导出及备份的首版 | 累计约 7–12 个开发日 | 识别边界稳定、导入格式确认、数据安全验证 |

等待用户安装、权限开启和反馈的时间另计；后台稳定性需要跨夜观察。若系统或应用无法暴露可靠付款信息，会调整覆盖方式与计划，不以猜测填补。每次里程碑后依据实际结果修订估算。

## 需要用户参与的节点

- 首个 APK 的下载、系统安装授权及启动反馈。
- 确认手机 Android/系统版本、微信及支付宝等目标应用版本。
- 按说明开启手机无障碍、通知读取及实际必要的系统设置。
- 进行真实支付场景验证并反馈必要的结构化结果；无需为覆盖全部场景专门消费，不上传真实完整账单。
- 导入格式适配确需样本时，优先使用虚构或脱敏样本；真实账单继续保留在用户手机。

## 每轮交付记录

交付说明统一包含：

1. 本轮实现内容及对应源码提交。
2. APK 版本、包名、最低系统要求、签名用途、下载链接和校验值。
3. 「代码已实现」「模拟或自动化测试通过」「用户手机真机实测通过」分别列证据，未完成项写待验证。
4. 权限设置、安装更新及本轮真机测试步骤。
5. 已知限制、不可自动捕获的来源和补记办法。
6. 下一步及需要用户完成的具体操作。
